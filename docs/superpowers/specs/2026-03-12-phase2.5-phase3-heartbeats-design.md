## Frontend Pages

### /org - Organization Architecture Page

**Layout:**
- Left sidebar: Org tree (React Flow) - collapsible
- Right panel: Details/edit form (tabbed: Node Details, Roles, Members)

**Features:**
- Draggable nodes, zoom controls, auto-layout
- Create/edit/delete org nodes with modal form
- Role management (CRUD with permissions tags)
- Member management with role assignment
- Search/filter by department or name

**APIs Called:**
- `GET /api/org/chart` - Get org chart data
- `POST /api/org/chart/nodes` - Create org node
- `PUT /api/org/chart/nodes/{id}` - Update org node
- `DELETE /api/org/chart/nodes/{id}` - Delete org node
- `GET /api/org/roles` - Get roles
- `POST /api/org/roles` - Create role
- `GET /api/org/members` - Get members
- `POST /api/org/members` - Create member

### /goals - Goal Management Page

**Layout:**
- Top: Goal cards grid with progress bars
- Bottom: Goal alignment graph (linked parent-child goals)

**Features:**
- Goal CRUD with priority/status badges
- Progress tracking (0-100% slider)
- Parent-child goal alignment (visual links)
- Due date countdown
- Tag filtering and metrics display

**APIs Called:**
- `GET /api/org/goals` - Get all goals
- `POST /api/org/goals` - Create goal
- `PUT /api/org/goals/{id}` - Update goal
- `DELETE /api/org/goals/{id}` - Delete goal
- `POST /api/org/goals/align` - Create goal alignment

### /approvals - Approval Center Page

**Layout:**
- Top tabs: Pending, Approved, Rejected, All
- Main table: Approval requests with action buttons

**Features:**
- One-click Approve/Reject with comment modal
- Approval history timeline (expandable)
- Priority badges and due date warnings
- Bulk action support
- Real-time status refresh

**APIs Called:**
- `GET /api/org/approvals` - Get approvals (with status filter)
- `POST /api/org/approvals` - Create approval
- `POST /api/org/approvals/{id}/approve` - Approve
- `POST /api/org/approvals/{id}/reject` - Reject
- `GET /api/org/approvals/{id}/history` - Get approval history

### /audit - Audit Logs Page

**Layout:**
- Top filter bar (date range, user, action type, resource)
- Main table with expandable details

**Features:**
- Advanced filtering (multiple criteria)
- Pagination (50 per page default)
- Export to Excel/CSV
- Expandable row shows request/response JSON
- Summary statistics card

**APIs Called:**
- `GET /api/org/audit/logs` - Get audit logs (with filters)
- `GET /api/org/audit/summary` - Get audit summary

### /heartbeats - Heartbeat Configuration Page

**Layout:**
- Top: Status dashboard (active/inactive/failed counts)
- Main: Card grid of heartbeat tasks

**Features:**
- CRUD heartbeat configs (name, interval, action type, params)
- Toggle enable/disable with confirmation
- Manual trigger button with live log output
- Real-time status indicator (last run time, next run time)
- Execution history modal

**APIs Called:**
- `GET /api/heartbeats` - List all heartbeat configs
- `POST /api/heartbeats` - Create heartbeat config
- `GET /api/heartbeats/{id}` - Get single heartbeat
- `PUT /api/heartbeats/{id}` - Update heartbeat config
- `DELETE /api/heartbeats/{id}` - Delete heartbeat
- `POST /api/heartbeats/{id}/enable` - Enable heartbeat
- `POST /api/heartbeats/{id}/disable` - Disable heartbeat
- `POST /api/heartbeats/{id}/trigger` - Manually trigger
- `GET /api/heartbeats/{id}/logs` - Get execution history

## Backend Heartbeats Module

### Database Schema

**heartbeats table:**
```python
{
  id: str (UUID)
  name: str
  description: str
  action_type: str (check_agent_status, send_reminder, custom)
  action_params: dict (JSON)
  interval_seconds: int
  is_active: bool
  last_run_at: datetime | null
  next_run_at: datetime
  created_at: datetime
  updated_at: datetime
}
```

**heartbeat_logs table:**
```python
{
  id: str (UUID)
  heartbeat_id: str (FK)
  status: str (success, failed, running)
  result: dict (JSON) | null
  error_message: str | null
  started_at: datetime
  completed_at: datetime | null
}
```

### API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/heartbeats` | List all heartbeat configs |
| POST | `/api/heartbeats` | Create heartbeat config |
| GET | `/api/heartbeats/{id}` | Get single heartbeat |
| PUT | `/api/heartbeats/{id}` | Update heartbeat config |
| DELETE | `/api/heartbeats/{id}` | Delete heartbeat |
| POST | `/api/heartbeats/{id}/enable` | Enable heartbeat |
| POST | `/api/heartbeats/{id}/disable` | Disable heartbeat |
| POST | `/api/heartbeats/{id}/trigger` | Manually trigger (for testing) |
| GET | `/api/heartbeats/{id}/logs` | Get execution history |

### Scheduler Implementation

- APScheduler with `AsyncIOScheduler`
- Jobs run async, update `last_run_at` and `next_run_at`
- On execution: create heartbeat_log entry, execute action, update log status

## Data Flow

- Frontend Zustand stores for state management (matching existing pattern)
- API client in `frontend/src/api/heartbeats.ts` + `org.ts`
- Real-time updates via manual refresh (can add WebSockets later if needed)

## Error Handling

- Frontend: `message.error()` for API failures
- Backend: HTTPException with proper status codes
- Scheduler errors logged to `heartbeat_logs` table

## Testing

- Backend: pytest tests for Heartbeats service and router
- Frontend: Basic component tests for key components

## Implementation Approach

**Monolithic Sprint** - Build all 5 frontend pages + Heartbeats backend API in one sprint.

This ensures:
- Consistent UI/UX across all pages
- Backend and frontend tested together end-to-end
- Proper integration between heartbeat frontend and backend scheduler
