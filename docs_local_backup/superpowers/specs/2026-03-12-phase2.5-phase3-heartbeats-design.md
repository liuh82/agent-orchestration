## Backend Heartbeats Module

### Database Schema

**heartbeats table:**
```sql
CREATE TABLE heartbeats (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  action_type TEXT NOT NULL,  -- check_agent_status, send_reminder, custom
  action_params TEXT,  -- JSON
  interval_seconds INTEGER NOT NULL,
  is_active INTEGER DEFAULT 1,
  last_run_at TIMESTAMP,
  next_run_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**heartbeat_logs table:**
```sql
CREATE TABLE heartbeat_logs (
  id TEXT PRIMARY KEY,
  heartbeat_id TEXT NOT NULL,
  status TEXT NOT NULL,  -- success, failed, running
  result TEXT,  -- JSON
  error_message TEXT,
  started_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  completed_at TIMESTAMP,
  FOREIGN KEY (heartbeat_id) REFERENCES heartbeats(id) ON DELETE CASCADE
);

-- Index for foreign key lookups
CREATE INDEX idx_heartbeat_logs_heartbeat_id ON heartbeat_logs(heartbeat_id);
-- Index for time-based queries (most recent logs)
CREATE INDEX idx_heartbeat_logs_started_at ON heartbeat_logs(started_at DESC);
```

**Database Initialization:**
Enable WAL mode in init_db.py:
```python
def init_db():
    conn = sqlite3.connect('tasks.db')
    conn.execute('PRAGMA journal_mode=WAL;')
    conn.execute('PRAGMA foreign_keys=ON;')
    # ... create tables
```

### Scheduler Implementation

- APScheduler with `AsyncIOScheduler` as singleton
- FastAPI lifespan events: start scheduler on startup, shutdown gracefully on exit
- Jobs run async, update `last_run_at` and `next_run_at`
- On execution: create heartbeat_log entry (status: running), execute action, update log status
- SQLite uses WAL mode for better concurrency
- Scheduler persists jobs: on restart, reloads active heartbeats from database and reschedules

**Lifespan Handler:**
```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    scheduler.start()  # synchronous call
    # Load and schedule all active heartbeats from database
    await load_and_schedule_heartbeats()
    yield
    # Shutdown
    scheduler.shutdown(wait=True)  # synchronous call with wait
```

**Job Reload Function:**
```python
async def load_and_schedule_heartbeats():
    """Load active heartbeats from DB and schedule them"""
    heartbeats = await heartbeat_service.get_active_heartbeats()
    for hb in heartbeats:
        scheduler.add_job(
            execute_heartbeat,
            'interval',
            seconds=hb.interval_seconds,
            args=[hb.id],
            id=f"heartbeat_{hb.id}",
            replace_existing=True
        )
```

## Data Flow

- Frontend Zustand stores for state management (matching existing pattern from `agents.ts`)
- API client in `frontend/src/api/heartbeats.ts` + `org.ts`
- Error handling: stores use `message.error()` from Ant Design for API failures
- Real-time updates via polling (15-30s intervals) - WebSockets can be added later if needed

**Polling Implementation Pattern:**
```typescript
// In store or component
useEffect(() => {
  const interval = setInterval(() => {
    fetchHeartbeats(); // refresh status
  }, 15000); // 15 seconds
  return () => clearInterval(interval);
}, []);
```

## Error Handling

- Frontend: `message.error()` for API failures, matching existing pattern
- Backend: HTTPException with proper status codes (400 for validation, 404 for not found, 500 for server errors)
- Scheduler errors logged to `heartbeat_logs` table with error_message field

## Testing

- Backend: pytest tests for Heartbeats service and router in `tests/test_heartbeats.py`
- Frontend: Basic component tests for key components (OrgChart, Heartbeats card)

## Implementation Approach

**Monolithic Sprint** - Build all 5 frontend pages + Heartbeats backend API in one sprint.

This ensures:
- Consistent UI/UX across all pages
- Backend and frontend tested together end-to-end
- Proper integration between heartbeat frontend and backend scheduler

**Phased Delivery (Optional fallback):**
If issues arise, can break into:
- Phase A: Backend Heartbeats API (models, service, router, scheduler)
- Phase B: Frontend Org + Goals pages
- Phase C: Frontend Approvals + Audit pages
- Phase D: Frontend Heartbeats page
